# T0 — Why "Baselines 0 / 7" doesn't move for a Garmin tester

Debugger, 2026-10-22. Code read: app `main` d9fc265 and `1eb5192` (the tester's build `20261021.141128`, the 14:11 UTC
build of #16); platform `../plattform` at b306a96 (read-only). Whether the *deployed* platform equals that tree is not
checked. The user's data was not read.

## Verdict: partly confirmed

| Claim | Verdict |
| --- | --- |
| Platform: with RHR + sleep and no HRV, `baseline_days` is 0 and `calibrating` is true for good | **Confirmed by code** (below). It is the platform's documented rule, not a bug. |
| Garmin Connect doesn't write HRV to Apple Health | **Unproven here.** Vendor fact, belongs to the research ticket. The code doesn't care. The evidence request below settles it for this account. |
| App: the hint shows "Connect" instead of "Garmin Connect" | **Confirmed.** It is `HKSource.name`, passed through unchanged. |
| App: "Scoring your latest data" stays up although nothing new arrived | **Refuted as stated.** It is local, cannot outlive 5 min, and only follows an upload that sent something. It is mislabelled for this case, not stuck. |
| Premise: readiness is null in the row | **Contradicted.** The platform never writes `recovery` without `readiness`. |

Conclusions that depend on the vendor research: only "why HRV is absent". Everything else below holds either way.

### 1. Platform logic, file:line (`../plattform/backend/internal/scoring/`)

1. HRV for a night: mean of `hrv_sdnn` samples in [sleep start − 1 h, sleep end + 2 h], `compute.go:163`. No samples: `nil`.
2. RHR: last `resting_hr` sample of the day, else of the day before, `compute.go:166–168`. No samples: `nil`.
3. The baselines are built from the stored rows of the 30 scored days before (`ScoreHistory`, `store.go:611`, `LIMIT 30`
   rows; called at `compute.go:172`). A row counts for HRV only if `hrv_ms` is non-null (`compute.go:189–191`) and for RHR
   only if `rhr` is non-null (`compute.go:192–194`). `NewBaseline` has `N = len(values)` (`algorithms.go:36`).
4. `BaselineDays = min(lnHRVBase.N, rhrBase.N)`, `compute.go:355`. `Calibrating = lnHRVBase.N < 7 || rhrBase.N < 7`,
   `algorithms.go:170` (`MinBaselineDays = 7`, `algorithms.go:28`). `docs/API.md:603–604` documents exactly this.
5. A day with no HRV samples stores `hrv_ms = NULL`, so `lnHRV` stays empty, `lnHRVBase.N = 0`, `baseline_days = 0`,
   `calibrating = true`. No later day changes that, however much history exists. The counter cannot move without an
   HRV sample on some night.
6. Recovery is still computed. `Recovery` adds only the components that exist (`algorithms.go:141–166`; weights HRV .45,
   RHR .25, sleep .25, resp .05, renormalised). `compute.go:285–287` stores `recovery`, `compute.go:292–299` stores
   `readiness` whenever `recovery != nil`. `ReadinessState` returns `calibrating` for `calibrating == true`
   (`algorithms.go:211–214`). So the real row is `{recovery: 74, readiness: <number>, state: "calibrating",
   calibrating: true, baseline_days: 0, hrv_ms: null}`. Readiness is not null. The brief's `readiness: null` can only
   come from a day with no recovery at all.

**Other things that could hold the counter at 0 (none is needed for the verdict):**
- **RHR missing as well.** `user_sources.kind` can't tell it apart: heart rate, resting HR and VO2max all map to kind
  `hr` (`model.go:87`). So "newest hr" in `scripts/user.sh` proves nothing about RHR. Only `daily_scores.rhr`, or the
  app's Streams row, does.
- **Recovery 74 may be sleep alone.** With no HRV and no RHR, recovery equals sleep performance (the one component
  renormalises to 1). Compare `sleep_performance` with 74 (evidence step 4). With RHR present but no history, its score
  is a flat 50 (`z` returns 0 for `N == 0`, `algorithms.go:86–88`), which pulls recovery toward 50.
- **HRV exists but outside the window.** HRV is averaged only inside the sleep window (`compute.go:160–163`). A source
  that stamps one nightly value at the wake time or at midnight falls outside it. Vendor-dependent.
- **Sleep gating: none for the counter.** A day without sleep still gets a row and still counts for any baseline it has
  data for. Without sleep, the HRV window falls back to `NightWindow(d)` (`compute.go:159–161`).
- **Backfill order.** `scoreEvent` scores each event's days oldest first (`cmd/scoring/main.go:182`), but a later page
  of older days does not rescore newer ones, and `refreshActive` rescores only yesterday and today. That can leave a
  stale `0` for an HRV-capable user after a first import, but not for an account that never had HRV. Rule it out with
  `days_with_hrv_14d` (evidence step 3).
- `details.baseline_days` (`compute.go:329`) counts HRV nights only. The typed `baseline_days` is the minimum. Frozen
  by API.md, harmless, but they differ.

### 2. App behaviour

**What the app uploads (source-agnostic).** `HealthKitManager.swift:52–55`: HRV only from
`HKQuantityType(.heartRateVariabilitySDNN)`; resting HR from `.restingHeartRate`; respiratory rate from
`.respiratoryRate`; SpO2 from `.oxygenSaturation`. All are anchored queries with no source predicate
(`quantityPage`, `HealthKitManager.swift:128–141`), so they are uploaded from any source that writes them. Source name
and bundle ID go along per sample (`:220–228`). The app derives nothing (rule 3: the phone computes no scores). Only HRV,
sleep and workouts are *observed* for background delivery (`:187`).

**Gauge and copy.** Same input in both builds: `calibrating: true`, `baseline_days: 0`, `hrv_ms: nil`, 90 days of scored history.
- **`1eb5192` (tester's build).** `TodayStates.hero`: `if let today = f.today, today.calibrating { return .calibrating(nights: today.baselineDays) }`.
  The gauge reads "Baselines 0 / 7" and the sentence "Learning your baseline — 7 nights to go." (`ReadinessCopy.swift:27`,
  `nightsToGo = max(1, 7 − baselineDays)`, `Models.swift:305`), whatever the readiness. That is the screenshot.
- **`d9fc265` (main).** `TodayPresentation.decide` (`TodayViewModel.swift:762`). The cached history is 90 days
  (`AppState.historyDays`), so `prior.count >= 7`.
  - Row D (`:795`) needs 7 prior days with both HRV and RHR. A Garmin tester without HRV has 0, so it is skipped.
  - Row B "long history" (`:804`) wins. With the platform's real row (readiness a number): the gauge shows the
    **readiness number**, tiles unchanged without a "calibrating" caption, and the note "Baselines need heart-rate
    variability and resting heart rate from nights with your watch." (`:822–826`). The sentence is "Your baselines are
    still forming.".
  - With `readiness: null` (the brief's shape): gauge `.baselines(nights: vitals)`, where `vitals` counts prior rows with
    both HRV and RHR. So "Baselines 0 / 7" again, now with that note under it.
  - With fewer than 7 scored prior days it falls to `:809`: `.baselines(nights: today.baselineDays)`, 0 / 7, tiles
    captioned "calibrating", no note. That would still look stuck.
  - Verified: `TodayPresentationTests` (`row4B_aLongHistoryWithoutHRVShowsTheReadinessAndWhy`,
    `row4B_aLongHistoryWithoutHRVOrReadinessCountsHeartRateNights`, `row4B_aShortHistoryCountsTodaysBaselineDays`,
    `row3D_needsSevenNightsWithVitals`; 19 tests in the suite) all pass on d9fc265 in a scratch worktree (iPhone 17e, Unit plan, `-only-testing:RyftTests/TodayPresentationTests`).
    They already encode this account type ("a phone-only account (no HRV)"). No new test was written.
  - **What main still doesn't say:** the note says "from nights with your watch", which is wrong when the watch simply
    writes no HRV to Apple Health. A Garmin owner does wear the watch. Copy for that case belongs to a later ticket.

**"Scoring your latest data".** `SyncLine.scoring(night: false)` (`TodayViewModel.swift:539`) comes from
`TodayStates.line` at `:664`: `if f.phase == .awaitingScores { return .scoring(night: night) }`, with `night` false when the hero isn't pending.
- It is driven by the **local sync phase**, not by `/v1/me/sync` directly. `.awaitingScores` is reported only after an
  upload that returned a non-empty `touched` (`SyncCoordinator.swift:330–337`). With nothing uploaded the pipeline goes to
  `.refreshing` and the line shows "Updating…" or "Up to date".
- It ends when `GET /v1/me/sync` stops listing the touched days as pending, **or after 300 s at most**
  (`maximumScoringWait`, `:105`, same in `1eb5192`), then `.refreshing`. It cannot stay up indefinitely on this path.
  The other path, `scoring(night: true)` (`:669`), is the platform's `pending`.
- So at 10:38 the spinner means this foreground sync did upload something. Likeliest: the iPhone's own steps or active
  energy, which count as `touched` like any record. The stale-source hint looks only at **heart rate**
  (`newestRecords`, `HealthStore.swift:229`, falls back to sleep), so the two lines don't contradict each other. The hint
  says the watch is quiet, the line says the iPhone's data is being scored.
- Not proven: that the screenshot caught it for seconds and not minutes. Sync details → Streams (steps, last page) would show it.
- Wording: "Scoring your latest data" is true but reads as "your tracker's data". Product decision for the UI ticket.

**Source name.** `WatchSyncHint.source` is `SourceFreshness.source` = `HKSource.name` (`HealthStore.swift:252`). The hint
interpolates it verbatim (`TodayViewModel.swift:583–585`: "Nothing new from \(source) since \(time). Open the \(source)
app…"). Garmin's HealthKit source is named "Connect" (the screenshot). The app already has the bundle ID
(`SourceFreshness.bundleID`, `com.garmin.connect.mobile`) and uses it only for `isApp`. There is no name mapping (the only
"Garmin Connect" strings are copy and mock data). Fix shape: a small bundle-ID → display-name table with the HealthKit
name as fallback, used by the hint, the raw-night card and anywhere else `source.name` is shown. Rule 7 allows data-source
names stated factually.

**A contradiction in the repo itself.** `HealthKitManager.swift:3–6` ("Garmin Connect writes heart rate, resting HR,
HRV, respiratory rate, SpO2, sleep … into Apple Health") and the setup copy (`StatusViews.swift:658`,
`HealthPermissionView.swift:951`, `ProfileView.swift:363`) assume Garmin delivers HRV. If the vendor research says it
does not, that comment and those strings overpromise. Depends on the vendor-facts ticket.

### Things the brief should know

- This is the **same device and build** as the 2026-10-21 incident (iPhone17,1, iOS 27.0.1, `20261021.141128`). Root cause 3
  there left two hypotheses open: "today scored before its earlier days" or "no HRV/RHR". This ticket's reading favours
  the second. The evidence request tells them apart: `days_with_hrv_14d` of 0 means no HRV; a positive number with
  `baseline_days` 0 keeps the backfill-order hypothesis alive.
- For such an account the counter can't move **for a platform reason**. Whatever the app shows, the fix is on the
  platform or in the account's setup (another HRV source, or a different rule). Candidate `API_REQUESTS.md` items: a
  `calibrating` that only waits for baselines the account can have, or a field naming the missing input
  (for example `baseline_missing: ["hrv"]`). A request to the platform agent, not an app change.
- `readiness` is a number while calibrating, and main shows it. Tiles and the Trends chart already did.

## Evidence request for the user

All read-only. The debugger ran none of it.

**On the phone**
1. **Profile → Data → Sync details → Streams** (`ProfileView.swift:412`, `:614–640`). Screenshot the rows **HRV**, **Resting
   heart rate**, **Respiratory rate**, **Heart rate**, **Sleep**. Each shows a sent count, the newest date and "N accepted
   · N duplicates" for the last page. "Nothing sent yet" on HRV means HealthKit has no HRV the app may read.
   (There is no "Data sources" screen on main: `UserSource` from `GET /v1/me` is decoded and never shown.)
2. **Apple Health → Browse → Heart → Heart Rate Variability → Show All Data**: the newest entries and the source each
   names (Apple Watch, Garmin "Connect", something else, or no data). Same for **Resting Heart Rate**. Also **Health →
   profile picture → Apps → RYFT**: HRV and resting heart rate must both be on.

**On the platform (operator; `../plattform` is not edited)**

3. `scripts/user.sh <id|short id|email> [--json]` (usage in its header; needs `ADMIN_API_KEY`, else terraform output of
   `infra/vault`, else Vault, via `scripts/lib/admin.sh`). Read `data (14 days)  scored N, with stages N, with HRV N` and
   the `newest:` line. **Expected: `with HRV 0`** and no `hrv` among the newest kinds. (The map is per source *kind*, so `hr`
   also covers resting HR and VO2max.) `days_with_hrv_14d` counts `daily_scores.hrv_ms IS NOT NULL` (`store/admin.go:166`),
   which is exactly the baseline's input.
   `user.sh` does **not** print `User.sources`. For source name and kinds use `scripts/beta_report.sh` (one line per
   tester, the `sources` column is `name:kind,kind`, e.g. `Connect:hr,sleep,steps`). Expected: no `hrv` kind on the Garmin source.
   So the brief's "`scripts/user.sh <id>` for `User.sources` kinds" is `beta_report.sh`; `user.sh` gives `days_with_hrv_14d`.
4. The last 14 days of rows. **No operator script or admin route exists for `GET /v1/days`**; it needs the tester's own
   bearer token. (`scripts/smoke.sh` takes a token but also posts synthetic data: never on a real account.
   `scripts/print_days.py` only pretty-prints a `/v1/days` JSON array from stdin.) So read the table, on the access path you
   already use for production, read-only:
   ```sql
   SELECT day, recovery, readiness, state, calibrating, baseline_days, hrv_ms, rhr, resp_rate,
          sleep_performance, details->'recovery' AS recovery_components
   FROM daily_scores
   WHERE user_id = '<full user id>' AND day >= current_date - 14
   ORDER BY day DESC;
   ```
   Or, if you hold a token for that account, `GET /v1/days?from=<today-14>&to=<today>` piped into `scripts/print_days.py`.
   **Expected:** `baseline_days` 0, `calibrating` true, `hrv_ms` null on every row, `readiness` a number.
